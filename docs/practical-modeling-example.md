# Пример: от входных строк к реляционной модели

Этот пример показывает, как применять [правила моделирования](data-modeling-standard.md) к новому источнику. Предметные условия и исходные строки **вымышлены для обучения**; эксперимент PostgreSQL в разделе 10 действительно проведён на этих синтетических данных. Пример не описывает путевые листы или действующий источник DDC.

Разделы 1–9 посвящены логической модели и диагностическим запросам без создания таблиц. Раздел 10 — отдельный контролируемый опыт PostgreSQL 18: он использует DDL только в одноразовой тестовой базе. Примеры не задают производственную модель.

## 1. Что сообщил источник

Допустим, утверждён учебный контракт выгрузки заявок на работы:

1. Каждая входная строка описывает **одну работу в заявке**. У заявки может быть несколько работ; в этой выгрузке заявка без работ не передаётся.
2. Заявка определяется **кодом организации и номером заявки**. Оба значения обязательны. Номера выдаются независимо в каждой организации, не переиспользуются и сохраняются за той же заявкой. Коды организаций также устойчивы.
3. У работы есть номер внутри заявки. Он обязателен, не переиспользуется для другой работы и не меняется при исправлении её атрибутов.
4. Дата заявки и вид работы обязательны. Для всех строк одной заявки дата одинакова. Дату и вид работы разрешено уточнять, но контракт пока **не определяет порядок и способ принятия исправлений**.
5. Продолжительность указана в минутах, не может быть отрицательной. `0` означает известную нулевую продолжительность, `NULL` — продолжительность не сообщена.
6. Поступление содержит отдельные сообщения, а **не полный снимок** всех заявок. Отсутствие строки не означает удаления.

Это условия примера, а не выводы из вида файла. Если реальный поставщик не подтвердил такое правило, пользоваться им как доказательством нельзя.

## 2. Входные строки

| Организация | Номер заявки | Дата | Номер работы | Вид работы | Минуты |
|---|---|---|---|---|---:|
| СЕВ | 101 | 2026-01-05 | 1 | Осмотр | 30 |
| СЕВ | 101 | 2026-01-05 | 2 | Ремонт | `NULL` |
| ЮГ | 101 | 2026-01-06 | 1 | Осмотр | 0 |
| СЕВ | 102 | 2026-01-07 | 1 | Доставка | 50 |

В таблице **четыре строки о работах**, но **три разные заявки**. Считать число строк количеством заявок было бы ошибкой.

## 3. Проверяем гипотезы о ключах

**Гипотеза А:** номер заявки однозначно определяет заявку.

**Что её опровергнет:** один номер, выданный разным заявкам.

**Результат:** номер `101` есть у организаций СЕВ и ЮГ. Это разные заявки по учебному контракту.

**Вывод:** одного номера недостаточно. Гипотеза опровергнута.

**Гипотеза Б:** пара «организация, номер заявки» определяет заявку.

**Что её опровергнет:** повторное использование такой пары для другой заявки, пустая часть ключа или изменение кода, из-за которого теряется тождество.

**Результат:** в четырёх входных строках обнаружены три пары: `(СЕВ, 101)`, `(ЮГ, 101)`, `(СЕВ, 102)`. Пара `(СЕВ, 101)` повторяется из-за двух работ, а не из-за двух заявок. Уникальность на уровне заявки установлена **по условию учебного контракта**, а не по этим четырём строкам.

Проверка минимальности: без организации совпадают заявки с номером `101`; без номера совпадают разные заявки организации СЕВ.

**Вывод:** в пределах *заданного учебного контракта* это предметный ключ заявки.

**Гипотеза В:** для работы достаточно пары «организация, номер работы».

**Результат:** у СЕВ работа `1` встречается в заявках `101` и `102`. Гипотеза опровергнута.

По условию контракта ключ работы состоит из **организации, номера заявки и номера работы**. Каждая компонента необходима: удаление любой приводит к совпадению разных работ в приведённых строках.

Важно: отсутствие дублей на четырёх строках само по себе означает лишь уникальность *проверенной выборки*. Стабильность и предметный смысл ключей здесь опираются на текст учебного контракта.

## 4. Определяем отношения

| Отношение | Смысл одной строки | Возможный ключ | Связи и `NULL` |
|---|---|---|---|
| Заявка | Существует заявка данной организации с установленным номером и датой | Организация + номер заявки | Дата обязательна; у заявки может быть несколько работ |
| Работа заявки | В заявке есть работа с установленным номером, видом и продолжительностью | Организация + номер заявки + номер работы | Обязательная ссылка на заявку; вид работы обязателен; `NULL` в минутах означает «не сообщено» |

Каждая переданная работа относится **ровно к одной заявке**. В выгрузке представлены только заявки с работами; это не доказывает, что заявка без работ невозможна в предметной области. Минимальная кратность работ для всех заявок — **NOT VERIFIED**. Требование «хотя бы одна работа» в модель не вводится.

Функциональная зависимость «организация + номер заявки → дата заявки» следует из **условия контракта**. Её стоит проверить на поступлениях: разные даты у одной пары означали бы противоречие, требующее разбирательства.

Напротив, «номер заявки → организация» не выполняется: это показано контрпримером с номером `101`.

Вид работы и продолжительность описывают **одну и ту же работу**. Нельзя разнести их в два независимых множества и затем соединять по заявке: получились бы ложные сочетания. Независимость многозначных фактов здесь не установлена.

## 5. Какие ограничения следуют из модели

Если предметные условия контракта будут подтверждены для реального источника, потребуется рассмотреть:

- Первичный или уникальный ключ заявки из организации и номера.
- Ключ работы из трёх компонент и обязательную внешнюю ссылку на заявку.
- Обязательные значения для частей ключа, даты и вида работы.
- Ограничение неотрицательной продолжительности с сохранением различия между `0` и `NULL`.

Отдельный суррогатный идентификатор, справочник организаций, история состояний, триггер и таблица соответствий из этого примера **не следуют**. Для каждого понадобилось бы собственное основание.

Здесь перечислены **следствия условной логической модели, а не готовые ограничения действующей БД**. Достаточность конкретного механизма PostgreSQL проверяется отдельно.

## 6. Что ещё нельзя решить

Контракт допускает исправления, но не устанавливает, какое из двух противоречащих сообщений следует считать действующим.

**Контрпример:** сначала пришла работа `(СЕВ, 101, 2)` с видом «Ремонт», затем та же работа с видом «Осмотр». Оба сообщения относятся к одному ключу, но какое значение авторитетно — неизвестно.

**Статус: BLOCKED.** Нельзя брать последнюю строку файла, максимальную дату получения или произвольное значение. Требуется уточнить договорённость об исправлениях и порядке состояний.

Поскольку вход не является полным снимком, **отсутствующая работа не удаляется**. Это уже следует из пункта 6 учебного контракта.

Не определены и требования к хранению старых состояний и происхождению конкретных результатов. Поэтому историю и техническую трассировку заранее не проектируем.

## 7. Как записать доказательство

Ниже — образец записи для решения о ключе заявки.

| Поле | Запись |
|---|---|
| Утверждение | Организация + номер заявки определяют одну заявку |
| Основание | Пункт 2 **учебного** контракта; приведённые четыре строки |
| Что опровергнет | Повторное назначение той же пары другой заявке; изменение компоненты ключа; `NULL` |
| Проверка | Сверить правила нумерации с контрактом; найти совпадения и противоречия в данных; проверить каждую часть ключа |
| Полученный результат | 4 строки; 3 пары организации и номера; `(СЕВ, 101)` встречается дважды из-за разных работ |
| Статус | `STATIC VERIFIED` для содержания учебного контракта; наблюдение по четырём учебным строкам не доказывает реальную предметную уникальность |
| Ограничения | Нет настоящего поставщика, реальных данных и испытаний PostgreSQL |
| Решение | Использовать составной ключ **только в учебной логической модели**; для реального источника решение не принято |

Для реального решения одной таблицы из этого раздела недостаточно. Проверку нужно выполнить на доступной совокупности данных, сохранить исходный результат и назвать пределы применимости.

**Итог примера:** мы получили две обоснованные *внутри вымышленного контракта* сущности разной зернистости, отвергли два неверных ключа и остановились там, где не хватает правил изменения состояния. Именно такая остановка — правильный результат проектирования, а не недоработка.
## 8. Диагностические запросы: проверяем гипотезы

Ниже — **только читающие SQL-запросы**. Они используют строки раздела 2 прямо в `VALUES`, поэтому не требуют таблиц, миграций или прав на изменение данных. Каждый запрос можно выполнить отдельно в PostgreSQL 18.

Прежде чем проверить реальные данные, нужно определить их доступную совокупность, период и ограничения охвата. Проверка четырёх строк ниже ничего не доказывает о другом источнике.

### 8.1. Сколько заявок, работ и известных значений

```sql
WITH input(org_code, request_no, work_no, minutes) AS (
    VALUES
        ('СЕВ', 101, 1, 30),
        ('СЕВ', 101, 2, NULL::integer),
        ('ЮГ',  101, 1, 0),
        ('СЕВ', 102, 1, 50)
)
SELECT
    COUNT(*) AS input_rows,
    COUNT(DISTINCT (org_code, request_no)) AS requests,
    COUNT(DISTINCT (org_code, request_no, work_no)) AS works,
    COUNT(minutes) AS reported_minutes,
    COUNT(*) FILTER (WHERE minutes = 0) AS zero_minutes,
    COUNT(*) FILTER (WHERE minutes IS NULL) AS unknown_minutes
FROM input;
```

**Ожидаемый результат по учебным значениям (не вывод PostgreSQL):**

| input_rows | requests | works | reported_minutes | zero_minutes | unknown_minutes |
|---:|---:|---:|---:|---:|---:|
| 4 | 3 | 4 | 3 | 1 | 1 |

Здесь `COUNT(minutes)` считает **значения продолжительности**, а не сумму минут. Наличие двух строк одной заявки не означает двух заявок.

### 8.2. Какие части ключа нельзя удалить

Контрпример к минимальности составного ключа ищем, по очереди исключая каждую часть. Для каждого сокращённого ключа ниже ищутся совпадения разных учебных работ.

```sql
WITH input(org_code, request_no, work_no) AS (
    VALUES
        ('СЕВ', 101, 1),
        ('СЕВ', 101, 2),
        ('ЮГ',  101, 1),
        ('СЕВ', 102, 1)
),
reduced AS (
    SELECT 'без организации' AS removed,
           request_no::text || '/' || work_no::text AS reduced_key
    FROM input
    UNION ALL
    SELECT 'без номера заявки',
           org_code || '/' || work_no::text
    FROM input
    UNION ALL
    SELECT 'без номера работы',
           org_code || '/' || request_no::text
    FROM input
)
SELECT removed, reduced_key, COUNT(*) AS matches
FROM reduced
GROUP BY removed, reduced_key
HAVING COUNT(*) > 1
ORDER BY removed, reduced_key;
```

**Ожидаемые группы совпадений (порядок строк несущественен):**

| Удалённая часть | Сокращённый ключ | Совпадений |
|---|---|---:|
| Организация | `101/1` | 2 |
| Номер заявки | `СЕВ/1` | 2 |
| Номер работы | `СЕВ/101` | 2 |

Таким образом, для четырёх учебных работ каждая компонента необходима. Но проверка минимальности на выборке **не устанавливает устойчивость и предметный смысл ключа**. Эти свойства в примере взяты из учебного контракта.

### 8.3. Проверка зависимости «заявка → дата»

```sql
WITH input(org_code, request_no, request_date) AS (
    VALUES
        ('СЕВ', 101, DATE '2026-01-05'),
        ('СЕВ', 101, DATE '2026-01-05'),
        ('ЮГ',  101, DATE '2026-01-06'),
        ('СЕВ', 102, DATE '2026-01-07')
)
SELECT org_code, request_no
FROM input
GROUP BY org_code, request_no
HAVING COUNT(DISTINCT request_date) > 1
    OR COUNT(*) FILTER (WHERE request_date IS NULL) > 0;
```

**Ожидаемый результат:** ноль строк. Это только отсутствие контрпримеров на четырёх учебных строках, а не доказательство функциональной зависимости для других данных.

**Статус:** вычисления по напечатанным значениям проверяемы статически; исполнение этих запросов на PostgreSQL 18 пока `NOT VERIFIED`. После выполнения следует сохранить версию сервера, текст запроса, фактический вывод и охват проверки, не подменяя ожидаемый результат фактическим.

## 9. Декомпозиция: как возникают ложные сочетания

Это **другой вымышленный случай**, не продолжение контракта из раздела 1.

Предположим, одна строка означает «человек выполняет конкретную работу в заявке»:

| Заявка | Работа | Исполнитель |
|---|---|---|
| 101 | Осмотр | Иван |
| 101 | Ремонт | Пётр |

**Гипотеза:** работы и исполнителей можно хранить независимо, разделив отношение на «заявка — работа» и «заявка — исполнитель».

**Что опровергнет:** после обратного соединения появится пара «работа — исполнитель», которой не было в исходном отношении.

```sql
WITH original(request_no, work_kind, performer) AS (
    VALUES
        (101, 'Осмотр', 'Иван'),
        (101, 'Ремонт', 'Пётр')
),
works AS (
    SELECT DISTINCT request_no, work_kind
    FROM original
),
performers AS (
    SELECT DISTINCT request_no, performer
    FROM original
),
reconstructed AS (
    SELECT w.request_no, w.work_kind, p.performer
    FROM works AS w
    JOIN performers AS p USING (request_no)
)
SELECT request_no, work_kind, performer
FROM reconstructed
EXCEPT
SELECT request_no, work_kind, performer
FROM original;
```

**Ожидаемые ложные строки (не фактический вывод PostgreSQL):**

| Заявка | Работа | Исполнитель |
|---|---|---|
| 101 | Осмотр | Пётр |
| 101 | Ремонт | Иван |

Исходное отношение содержит две строки, обратное соединение — четыре. Две новые пары ничего не говорят о действительных назначениях.

**Вывод:** предложенная декомпозиция не сохраняет смысл этого учебного отношения. Два отдельных множества допустимы лишь при **независимости, установленной предметным правилом**. Одно только отсутствие контрпримеров в текущей выборке такую независимость не доказывает.

**Статус:** ожидаемые множества выведены из двух учебных строк; запуск SQL на PostgreSQL 18 — `NOT VERIFIED`.

## 10. Отдельный технический опыт: конкурентная запись T1/T2

Это **отдельный технический опыт**, не часть модели заявок из разделов 1–8.

**Условный инвариант:** в одной заявке одновременно может быть не больше двух назначенных людей. Сначала назначен один. Две операции назначения читают число участников и добавляют по одному, если число меньше двух.

**Гипотеза:** проверки `COUNT(*) < 2` перед каждым `INSERT` достаточно при `READ COMMITTED`.

**Что её опровергнет:** обе транзакции увидят одного участника, добавят разных людей и успешно завершатся, оставив в одной заявке трёх участников.

### 10.1. Подготовка изолированного стенда

**Только для отдельной одноразовой базы PostgreSQL 18. Не выполнять в DDC и не добавлять как миграцию.**

Здесь DDL нужен исключительно для воспроизводимого опыта. Он не предлагает производственную схему.

```sql
SELECT current_setting('server_version') AS pg_version,
       current_database() AS database_name;

CREATE TABLE public.probe_request (
    request_no integer PRIMARY KEY
);

CREATE TABLE public.probe_assignment (
    request_no integer NOT NULL
        REFERENCES public.probe_request (request_no),
    person text NOT NULL,
    PRIMARY KEY (request_no, person)
);

INSERT INTO public.probe_request (request_no) VALUES (101);
INSERT INTO public.probe_assignment (request_no, person)
VALUES (101, 'Иван');
```

Ограничения стенда гарантируют уникальность назначения *конкретного человека*, но **не ограничивают количество разных людей** одной заявки. Это намеренное условие опыта.

### 10.2. Точное чередование команд

Откройте **два независимых соединения к одной тестовой базе**. Выполняйте команды строго в показанном порядке, не объединяя их в один скрипт.

| Шаг | Сеанс T1 | Сеанс T2 |
|---|---|---|
| 1 | `BEGIN ISOLATION LEVEL READ COMMITTED;` | — |
| 2 | `SELECT COUNT(*) FROM public.probe_assignment WHERE request_no = 101;` | — |
| 3 | — | `BEGIN ISOLATION LEVEL READ COMMITTED;` |
| 4 | — | `SELECT COUNT(*) FROM public.probe_assignment WHERE request_no = 101;` |
| 5 | `INSERT INTO public.probe_assignment VALUES (101, 'Анна');` | — |
| 6 | — | `INSERT INTO public.probe_assignment VALUES (101, 'Борис');` |
| 7 | `COMMIT;` | — |
| 8 | — | `COMMIT;` |

После обоих завершений в любом сеансе:

```sql
SELECT request_no, COUNT(*) AS assigned
FROM public.probe_assignment
GROUP BY request_no;
```

**Ожидаемое поведение по документации PostgreSQL 18:** на шагах 2 и 4 обе проверки показывают `1`, две разные вставки не нарушают объявленный составной PK, обе транзакции могут завершиться, итоговый `assigned = 3`. Это означало бы нарушение учебного инварианта.

**Фактический результат:** опыт выполнен на PostgreSQL 18.6 в одноразовой базе GitHub Actions. Вывод двух сеансов и итоговое состояние зафиксированы в разделе 10.3.

### 10.3. Протокол проведённого испытания

**Дата:** 12 октября 2026 года. **Среда:** GitHub Actions, отдельные контейнеры `postgres:18`, одноразовая БД `isolated_probe`. Версия сервера из журнала: `180006` (**PostgreSQL 18.6**).

[Исходный журнал задания](https://github.com/lazuale/department-data-core/actions/runs/38212343512) подтверждает успешное завершение опыта.

**CLAIM:** проверки `COUNT(*) < 2` перед вставкой достаточно для соблюдения лимита назначений при `READ COMMITTED`.

**FALSIFIER:** обе транзакции считают одного участника, добавляют разных людей и успешно фиксируются; итоговых назначений становится три.

**TEST:** две отдельные сессии PostgreSQL. Каждая следующая операция запускалась после подтверждения предыдущей, как в таблице раздела 10.2. Клиент использовал `psql -X -v ON_ERROR_STOP=1 -qAt`.

**RAW RESULT — существенные строки журнала:**

```text
PG_SERVER_VERSION_NUM=180006
FINAL_COUNT=3
101|Анна
101|Борис
101|Иван
ANOMALY_CONFIRMED=YES

=== T1 RAW OUTPUT ===
T1_BEGIN
T1_COUNT=1
T1_INSERT_OK
T1_COMMIT_OK
=== T2 RAW OUTPUT ===
T2_BEGIN
T2_COUNT=1
T2_INSERT_OK
T2_COMMIT_OK
```

**VERDICT:** гипотеза **опровергнута**. Оба клиента прочитали `1` и успешно зафиксировали вставки, но база сохранила три назначения вместо допустимых двух.

**STATUS:** `CONTROLLED PROBE` — аномалия воспроизведена на PostgreSQL 18.6 в указанном учебном сценарии.

**LIMITATIONS:** проверены один начальный набор, одно упорядоченное чередование и одна версия PostgreSQL. Лимит «не более двух» задан только для опыта. Это не утверждение о предметных ограничениях реального DDC. Механизмы устранения аномалии в данном опыте **не проверялись**.

**DECISION:** простая проверка количества перед отдельной вставкой при `READ COMMITTED` не обеспечивает описанный учебный инвариант. Выбор ограничения, блокировки или иного механизма для настоящей предметной модели — `BLOCKED` до установления её правил и проверки подходящих вариантов.

### 10.4. Что ещё предстоит проверить

Аномалия воспроизведена в разделе 10.3, но способы её предотвращения **не проверены**. Если в реальной предметной модели обнаружится такой же инвариант, необходимо установить подходящее средство:

- Можно ли выразить установленный предметный инвариант через типы, ключи или другие декларативные ограничения **без введения вымышленных предметных атрибутов**?
- Если недостаточно, можно ли синхронизировать действия через блокировку **существующей** строки заявки до проверки количества? Для опыта следует отдельно проверить `SELECT ... FOR UPDATE` и повторное чтение при `READ COMMITTED`.
- При проверке `SERIALIZABLE` нужно заново задать исходные данные и повторить такое же чередование. По документации возможен отказ одной транзакции с SQLSTATE `40001`; приложение должно повторять всю транзакцию. Это не рекомендация автоматически выбирать `SERIALIZABLE`.

Нельзя заменять блокировку фиктивным `UPDATE x = x`. Выбор механизма для реальной модели остаётся **`BLOCKED`** до установления её инварианта и проверки подходящих альтернатив.

Для ручного повторения нужен отдельный одноразовый стенд. Контейнеры проведённого GitHub Actions-теста уже остановлены. Если тестовая база сохраняется, очистите **только созданные там** объекты:

```sql
DROP TABLE public.probe_assignment;
DROP TABLE public.probe_request;
```

В новом протоколе также фиксируют версию PostgreSQL, два сеанса, порядок команд, ошибки, значения `COUNT(*)`, результаты `COMMIT` и итоговые строки. См. [изоляцию транзакций в PostgreSQL 18](https://www.postgresql.org/docs/18/transaction-iso.html) и [явные блокировки](https://www.postgresql.org/docs/18/explicit-locking.html).
