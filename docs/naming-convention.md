# Стандарт именования

## 1. Назначение

Документ задаёт единые правила именования SQL-объектов, технических идентификаторов, кодов, миграций, файлов и тестовых сценариев проекта.

Имя отражает устойчивый смысл объекта в пределах его архитектурной ответственности.

## 2. Общая форма

SQL-идентификаторы:

- именуются на английском языке;
- используют ASCII и `lower_snake_case`;
- соответствуют форме `[a-z][a-z0-9_]*`;
- допустимы как некавыченные идентификаторы PostgreSQL в соответствующем контексте;
- отражают собственный смысл объекта;
- используют один канонический термин для одного смысла;
- имеют длину до 63 байт включительно.

Примеры формы:

```text
source
source_id
processing_status
created_at
is_active
```

Проектные объекты, допускающие квалификацию схемой, в миграциях, серверном SQL, проверках и тестах указываются с именем схемы:

```text
meta.<object>
core.<object>
xref.<object>
```

Локальные псевдонимы, CTE и временные объекты используют локальную область имён запроса или сессии.

## 3. Канонический технический словарь

Для общих технических понятий используются следующие термины:

| Термин | Смысл |
|---|---|
| `source` | логический источник сведений |
| `dataset` | структурированный набор данных с определённым смыслом и зернистостью |
| `transport` | способ доставки данных |
| `load` | отдельное поступление набора данных |
| `processing` | отдельное применение правил к уже полученному входу |
| `record` | входная запись или её технически нормализованное представление |
| `rule` | формализованное правило |
| `result` | результат операции или проверки |
| `status` | состояние объекта или процесса |
| `type` | разновидность объекта |
| `error` | ошибка |
| `lineage` | происхождение результата и связь с использованным входом |
| `external_identity` | идентичность объекта во внешнем пространстве |
| `identity_resolution` | результат разрешения внешней идентичности |
| `version` | версия объекта, контракта или правила |
| `migration` | версионированное изменение структуры или серверного SQL |

## 4. Схемы, таблицы и представления

Архитектурные схемы:

```text
meta
raw
stg
xref
core
ops
etl
api
mart
```

Принадлежность к архитектурному слою выражается именем схемы. Имя объекта содержит собственный смысл:

```text
core.<subject>
```

Таблица именуется по смыслу строки существительным в единственном числе или устойчивым составным понятием.

Отношение с самостоятельным смыслом получает собственное смысловое имя. Простая связующая таблица использует составное имя связываемых предметов:

```text
<subject>_<related_subject>
```

Порядок компонентов отражает семантические роли связи.

Представление и материализованное представление именуются по предоставляемому смыслу.

Для `raw` и `stg` имя выводится из стабильного кода набора данных, определённого входным контрактом:

```text
<dataset_code>_record
```

`dataset_code`, используемый в SQL-имени `raw` или `stg`, уникален в проектном пространстве кодов наборов данных и соответствует форме `[a-z][a-z0-9_]*`.

Объекты `core` именуются по предметному смыслу. Объекты `ops` именуются по смыслу рабочего состояния, действия или проверки.

Для размерной модели `mart` используются формы:

```text
fact_<subject>
dim_<subject>
```

Остальные аналитические объекты именуются по предоставляемому смыслу.

## 5. Колонки

Внутренний идентификатор:

```text
<subject>_id
```

Отдельный внешний идентификатор:

```text
external_id
external_<subject>_id
```

Полная внешняя идентичность может состоять из нескольких семантически именованных компонентов.

Внешний ключ использует имя предмета или роли:

```text
<subject>_id
<role>_<subject>_id
```

Основные формы атрибутов:

| Смысл | Форма |
|---|---|
| стабильный код | `<subject>_code` |
| предметный номер | `<subject>_number` |
| имя | `<subject>_name` |
| описание | `<subject>_description` |
| примечание | `<meaning>_note` |
| тип | `<subject>_type` |
| статус | `<subject>_status` |
| количество объектов | `<subject>_count` |
| позиция | `<subject>_position` |
| денежное значение | `<meaning>_amount` |

Суффиксы `_id`, `_code` и `_number` обозначают соответственно идентичность, стабильный код и предметный номер.

Булевы поля:

```text
is_<state>
has_<property>
can_<action>
```

Конкретный момент времени:

```text
<event>_at
```

Календарная дата:

```text
<meaning>_date
```

Время суток:

```text
<meaning>_time
```

Период действия:

```text
valid_from
valid_to

effective_from
effective_to
```

Бизнес-время и техническое время получают самостоятельные семантические имена.

Позиция строки табличного источника:

```text
source_row_number
```

Эта форма применяется, когда позиция строки входит во входной контракт.

Измерение с фиксированной единицей:

```text
<measure>_<unit_token>
```

Измерение с переменной единицей:

```text
<measure>_value
<measure>_unit_code
```

Для безразмерных значений используются:

```text
<meaning>_ratio
<meaning>_fraction
<meaning>_percent
```

Для файлов и адресов:

```text
file_name
file_path
<subject>_url
<subject>_uri
```

## 6. Ограничения и индексы

Для именуемых ограничений и индексов используется закрытый набор форм:

| Объект | Форма |
|---|---|
| primary key | `pk_<table>` |
| foreign key | `fk_<table>_<relation>` |
| unique constraint | `uq_<table>_<meaning>` |
| check constraint | `ck_<table>_<rule>` |
| exclusion constraint | `ex_<table>_<meaning>` |
| explicit index | `idx_<table>_<purpose>` |

В имени внешнего ключа `<relation>` обозначает целевой предмет или семантическую роль связи.

Имя сложного ограничения или индекса передаёт устойчивый смысл объекта. Перечень колонок входит в имя, когда он остаётся кратким и полностью выражает назначение.

## 7. Функции и серверные объекты

Функция или процедура именуется как действие:

```text
<verb>_<object>
```

Параметры используют семантические имена.

Одно имя функции соответствует одной логической операции.

Самостоятельная последовательность:

```text
<subject>_sequence
```

Триггер именуется по выполняемому действию.

Пользовательский тип или домен именуется по предметному или техническому смыслу.

## 8. Роли

Групповые роли базового стенда используют форму:

```text
ddc_<responsibility>
```

Принятые роли:

```text
ddc_owner
ddc_loader
ddc_worker
ddc_analyst
```

Префикс `ddc_` обозначает проектные групповые роли. Имена этих ролей являются соглашением базового стенда. Имена персональных ролей с атрибутом `LOGIN` определяются средой эксплуатации.

## 9. Миграции, файлы и тестовые сценарии

Версионированная миграция:

```text
NNNN_<description>.sql
```

Нормативные и тематические Markdown-документы проекта используют `lower-kebab-case`:

```text
naming-convention.md
data-modeling-standard.md
```

Служебные файлы репозитория используют общепринятые имена соответствующего инструмента или платформы:

```text
README.md
LICENSE
```

Обычные SQL-файлы используют `lower_snake_case`. Каталоги используют lowercase ASCII.

Имя файла отражает назначение содержимого.

Стабильный идентификатор синтетического сценария:

```text
<SCOPE>-NNN
```

`SCOPE` — короткий стабильный uppercase ASCII-код области проверки. `NNN` — постоянный номер сценария. Один идентификатор соответствует одному сценарию на весь срок его существования.

## 10. Исходные имена и сокращения

Поля источника сохраняют связь с входным контрактом. Каноническое техническое имя выбирается после определения смысла поля.

Общеупотребимые технические сокращения применяются при устойчивом и однозначном смысле:

```text
id
url
uri
api
ip
uuid
```

Новый термин записывается полной формой. Сокращённая форма вводится отдельным проектным соглашением при устойчивом и однозначном употреблении.
