# Базовые требования к production-среде

## 1. База и структура

Рабочее ядро размещается в одной логической базе PostgreSQL со схемами:

```text
meta
raw
stg
xref
core
ops
etl
api
mart
```

Отдельные базы по годам, реестрам или отдельным Excel-файлам не являются стандартной моделью. Физическая инфраструктура может меняться без изменения этой логической структуры.

Для production используется поддерживаемая версия PostgreSQL. Переход между основными версиями выполняется как отдельная управляемая операция.

## 2. Миграции

Структура базы и серверный SQL-код хранятся в репозитории. Любое изменение DDL оформляется миграцией:

```text
db/migrations/
├── 0001_initial.sql
├── 0002_add_asset.sql
└── ...
```

К миграциям относятся таблицы, индексы, ограничения, представления, функции, процедуры и права.

Ручное изменение production-базы через SQL-клиент допустимо для диагностики только там, где оно не меняет структуру. Если структура изменилась, соответствующая миграция должна существовать в репозитории.

Пустая база должна разворачиваться до актуального состояния из содержимого репозитория без восстановления последовательности ручных действий.

## 3. Разработка и production

Эксперименты со схемой и тестовые изменения не выполняются на рабочих данных. Для разработки используется отдельная база или среда с совместимой структурой.

Полная инфраструктура DEV / TEST / PROD не обязательна для первой версии, но граница между экспериментом и production обязательна.

## 4. Роли и доступ

Клиентские подключения не являются владельцами схем и таблиц. Права выдаются по роли клиента и в минимальном объеме.

Типовое разделение:

| Роль | Доступ |
|---|---|
| владелец БД | структура и миграции |
| загрузчик | необходимые операции `raw` и `etl` |
| рабочий клиент | объекты `api` |
| аналитика | чтение `mart` |

Рабочий клиент не получает произвольный `UPDATE` внутренних таблиц. Аналитический клиент не изменяет рабочее состояние.

Секреты, пароли и production-строки подключения не хранятся в Git. В публичной документации не публикуются реальные адреса серверов, сетевые диапазоны и учетные данные.

PostgreSQL открывается только тем узлам и сетям, которым доступ действительно требуется.

## 5. Надежность загрузок

Каждая загрузка набора данных регистрируется в `meta`. Должны быть известны как минимум набор данных, время, статус и количество принятых строк.

Неуспешная обработка получает явный статус и не должна незаметно подменять рабочие данные частично подготовленным состоянием.

Операции, которые по смыслу составляют одно изменение, выполняются транзакционно.

Целостность закрепляется средствами PostgreSQL: `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL`, `CHECK` и другими ограничениями по необходимости. Клиентская валидация их не заменяет.

## 6. Резервное копирование

Production-база регулярно резервируется. Копия хранится отдельно от рабочего экземпляра PostgreSQL.

Наличие backup-файла недостаточно: процедура восстановления периодически проверяется на отдельной базе.

```text
backup
  ↓
restore
  ↓
проверка структуры и данных
```

`raw` позволяет повторно обработать уже полученные данные, но не заменяет резервную копию базы.

## 7. Производительность

Индексы создаются под реальные ограничения и запросы. В первую очередь учитываются первичные и уникальные ключи, связи, рабочие фильтры и аналитические выборки.

Не индексируется каждая колонка «на будущее» и не вводятся дополнительные архитектурные механизмы без измеримой причины.

При замедлении сначала определяется источник проблемы: SQL, план выполнения, индекс, объем результата, клиентская обработка, сеть или ресурсы сервера.

## 8. Наблюдаемость

Для первой версии достаточно контролировать:

- доступность PostgreSQL;
- свободное место;
- успешность резервного копирования;
- состояние и длительность последних загрузок;
- явные ошибки приложений.

Набор метрик расширяется вместе с реальной нагрузкой.

## 9. Обновление

Обновление production выполняется воспроизводимыми шагами: применяются миграции, обновляется серверный код, затем проверяются основные операции. Клиент обновляется только тогда, когда изменился его контракт.

Текущая версия структуры должна определяться по журналу примененных миграций.

## 10. Что не требуется в первой версии

Базовая архитектура не требует заранее внедрять высокую доступность, репликацию, Kubernetes, отдельный оркестратор, Row Level Security, партиционирование, отдельный application server или специализированное аналитическое хранилище.

Такие механизмы вводятся по фактическим требованиям и не должны менять базовые границы данных.
