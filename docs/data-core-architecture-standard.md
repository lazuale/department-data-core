# Архитектура базы данных DDC

## Сила нормативных утверждений

Эти значения действуют во всех трёх документах канона.

| Слово | Значение |
|---|---|
| **Обязательно** | нарушение означает несоответствие архитектуре |
| **Запрещено** | конструкция несовместима с архитектурой |
| **Допустимо** | один из корректных вариантов |
| **По умолчанию** | базовый вариант; отступление разрешено при условии, указанном в правиле |
| **Пример** | иллюстрация без нормативной силы |

Условное требование действует только при выполнении названного условия. Описание понятия не требует создания одноимённой таблицы или колонки.

Термины предметной модели определены в [M01](data-modeling-standard.md#m01-модель-и-зернистость), термины ключей — в [M02](data-modeling-standard.md#m02-идентичность-и-ключи).

## A01. Граница базы данных

**Обязательно:** DDC представляет одну логическую базу PostgreSQL. Схема — пространство имён объектов внутри этой базы. Разделение данных по периоду или набору не создаёт самостоятельные логические базы DDC.

## A02. Поступления и происхождение

| Понятие | Определение |
|---|---|
| Источник (`source`) | логический поставщик сведений с определённой областью ответственности |
| Набор данных (`dataset`) | набор внутри источника с определёнными смыслом и зернистостью входной записи |
| Поступление (`load`) | отдельно различаемый вход одного набора данных |
| Обработка (`processing`) | применение правил преобразования к полученному входу |
| Технический контракт | состав, исходное представление полей и правила их технического приведения |
| Идентификация поступления | различение входов и принадлежности их записей |
| Техническая трассировка | связь результата с входными записями и выполненными преобразованиями |
| Предметное происхождение | сведения, объясняющие предметное основание факта или значения |
| Audit | сохранённые сведения об изменениях и их авторах |
| Воспроизводимость | получение определённого результата заново из сохранённого входа, правил и иных использованных оснований |

**Обязательно:** если требуется техническая трассировка, сохраняемые связи представляют объявленную глубину трассировки: поступление, входную запись или преобразование. Идентификатор одного поступления без связей с остальным использованным входом не представляет трассировку результата нескольких поступлений.

**Допустимо:** представлять контекст источника и набора через связанные метаданные либо через однозначно закреплённый за SQL-объектом контекст. Отдельные каталоги источников и наборов, запись каждой обработки, status, счётчики, hash и технические поля в каждой предметной таблице из этих понятий не следуют.

**Допустимо:** хранить техническую трассировку отдельно от предметных таблиц. Её наличие, как и audit или воспроизводимость прошлых результатов, определяется конкретным требованием к данным. Предметное происхождение, являющееся частью смысла факта, относится к предметной модели.

## A03. Схемы и зависимости

**Обязательно:** объект проекта относится к ответственности одной из схем в таблице. Это единственный нормативный перечень схем DDC. Существование схемы не требует наполнения её таблицами.

В таблице «предметная ссылка» означает ссылку на сущность, факт или отношение модели. «Служебная ссылка происхождения» означает связь с поступлением или входной записью по A02. Конкретная необходимость соответствия `xref` определяется в [M04](data-modeling-standard.md#m04-внешняя-идентичность).

| Схема | Ответственность и границы зависимостей |
|---|---|
| `meta` | технические метаданные БД, контекст поступлений и обработки; не второй экземпляр предметных фактов |
| `raw` | представление полученного входа с контекстом и адресом записи по A04; предметное объединение источников здесь не выполняется |
| `stg` | техническая подготовка `raw` по A04; определения используют вход и его технический контракт |
| `xref` | сохраняемые соответствия внешней идентичности ключам объектов `core`; контекст внешнего ключа определяется источником и пространством идентификаторов; предметные атрибуты объекта здесь не дублируются |
| `core` | канонические сущности, факты и отношения; их смысл определяется предметной моделью независимо от формы источника; предметные ссылки ведут к каноническим объектам, служебные ссылки происхождения допустимы по A02 |
| `ops` | результаты работы с предметными данными: проверки, назначения, состояния и действия; предметные ссылки используют `core` и другие объекты `ops`; состояние работы с фактом не подменяет значение самого факта |
| `etl` | функции и процедуры преобразования; чтение, вызовы и запись в других схемах ограничены их ответственностью; самостоятельные наборы хранимых данных здесь не размещаются |
| `api` | SQL-представления, функции и процедуры с контрактами доступа по A05; внутренние зависимости операции определяются её контрактом, без собственного первичного предметного состояния |
| `mart` | производные аналитические таблицы, представления, материализованные представления и агрегаты; предметные значения выводятся из `core`, `ops` и других объектов `mart`; метаданные и входные записи допустимы как технический контекст, но не как альтернативные предметные факты |

**Запрещено:** использовать результат `mart` как первичное основание изменения предметного факта. Изменение производного представления не является исправлением его первичных данных.

## A04. RAW и STG

**Обязательно:** каждая сохранённая входная запись различима внутри поступления, а её поступление, набор и источник определяются однозначно. Адрес учитывает все части, без которых две записи одного поступления совпадают.

**Допустимо:** составной адрес либо отдельный идентификатор записи с ограничением уникальности её исходного адреса. Пара `(load_id, source_row_number)` — **пример**, применимый только при уникальном номере записи в поступлении.

**Запрещено:** после фиксации входа изменять его исходные значения в `raw`. Исправленный вход представляет другое поступление; повторная обработка использует сохранённый вход. Фиксация означает завершённое сохранение входа транзакцией БД. Это правило не задаёт срок хранения.

**Допустимо:** физически хранить входы разных источников в одной таблице, если их контекст и адреса сохраняются и технические контракты не смешиваются.

**Обязательно:** преобразование в `stg` сохраняет смысл входного значения по техническому контракту. Типизация, представление пустых значений и техническая нормализация определяются этим контрактом. Выбор предметного объекта, авторитетного значения и исправление по предметному смыслу находятся за этой границей.

**Допустимо:** реализовать `stg` представлением, материализованным представлением, таблицей либо результатом SQL-выражения без отдельного хранения.

`RAW → STG → CORE` обозначает логические границы представления входа, технической подготовки и предметной модели. Разрешение внешней идентичности включается по M04. Эта запись не задаёт порядок `INSERT` и не требует отдельной материализации каждого шага.

## A05. SQL-интерфейсы и права

Контракт SQL-интерфейса — определения параметров, типов и смысла результата, допустимых изменений данных и отказов операции.

**Обязательно:** контракт объекта `api` задаётся явно. Изменение внутренней таблицы само по себе не расширяет набор колонок публичного результата.

**Допустимо:** чтение через представления или функции; изменение через функции, процедуры либо изменяемое представление, если сохраняются инварианты [M06](data-modeling-standard.md#m06-ограничения-целостности) и [M09](data-modeling-standard.md#m09-изменение-состояния).

**Обязательно:** роль доступа к `api` получает прямой доступ к данным только через предусмотренные объекты SQL-интерфейса, без прав на внутренние таблицы и изменение постоянной структуры БД. Роль аналитического чтения получает доступ к данным только через предусмотренные объекты `mart` без прав изменения первичных данных. Имена ролей и способы входа не определяются этим правилом.

**Допустимо:** предоставление операции прав через `SECURITY DEFINER`.

**Обязательно:** для `SECURITY DEFINER` права владельца ограничены разрешёнными эффектами операции, разрешение имён исключает подмену объектов вызывающим, а круг ролей с `EXECUTE` указан явно. Автоматическое право `PUBLIC` не является основанием доступа, если контракт не разрешает исполнение всем ролям.
